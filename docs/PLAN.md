# План работ

## Задача

Расширение для AutoCAD 2021 для отображения и обработки атрибутики пунктов опробования
калийного месторождения. Требуется: пошаговый графический интерфейс, просмотр и
редактирование свойств существующего набора точек, добавление и удаление точек, расчёт
изолиний мощностей и поля распределения целевого параметра по указанной пользователем
области, отображение статуса расчёта, возможность приостановить расчёт с последующим
продолжением и полностью его прекратить. Данные читаются из Oracle Database.

Полное техническое задание — `Описание_задачи.docx` в корне репозитория.

## Технические решения

| Пункт | Решение |
|---|---|
| Язык и платформа | C# / .NET Framework 4.8 |
| API AutoCAD | Managed API через NuGet-пакет `AutoCAD.NET` 2021.x |
| Интерфейс | WPF, размещается в `PaletteSet` как пристыковываемая палитра |
| Доступ к БД | ODP.NET Managed, без установки Oracle Instant Client |
| Единица расчёта | Два режима: один слой либо произвольный набор слоёв |
| Задание области | Рисование контура в чертеже с живым превью (`PolylineJig`) |
| Интерполяция | IDW и ординарный кригинг за общим интерфейсом `IInterpolator` |

### Обоснование ключевых выборов

**.NET вместо C++/ObjectARX.** ТЗ допускает оба варианта, но ObjectARX 2021 требует строго
MSVC v142, GUI пришлось бы делать на MFC или Qt, а Oracle — через OCI. Managed API даёт тот
же результат при существенно меньшем объёме работы, а на реальных объёмах данных (182 пункта
опробования) выигрыш нативного кода в скорости отсутствует.

**Целевой фреймворк `net48` не является предметом выбора** — AutoCAD 2021 хостит именно
.NET Framework 4.8; переход на .NET 8 произошёл только в AutoCAD 2025.

**Два интерполятора вместо одного.** IDW прост, детерминирован и легко проверяется тестами.
Ординарный кригинг геостатистически корректнее для содержаний руды и даёт карту дисперсии
оценки. Возможность сравнить результаты двух методов на одних данных полезна сама по себе.

## Архитектура

```
src/Task.Core      netstandard2.0   модель данных, интерполяция, изолинии, доменная логика
src/Task.Data      net48;net8.0     доступ к Oracle
src/Task.Plugin    net48            команды AutoCAD, WPF-панель
tests/Task.Core.Tests   net8.0      модульные и интеграционные тесты
```

`Task.Core` не зависит ни от AutoCAD, ни от Oracle — только от интерфейсов. Это позволяет
разрабатывать и тестировать алгоритмическую часть, составляющую основную сложность задачи,
без запуска AutoCAD.

`Task.Data` мультитаргетится, потому что ODP.NET поставляется двумя разными пакетами:
`Oracle.ManagedDataAccess` для .NET Framework и `Oracle.ManagedDataAccess.Core` для .NET.

## Исходные данные

| Таблица | Строк | Содержимое |
|---|---|---|
| `GEOMETRY` | 5228 | `OBJECTGUID`, `SUBLAYERGUID`, `ID`, `GEOWKT` |
| `GPO` | 182 | `ID`, `X`, `Y`, `Z` — пункты опробования |
| `PROBA` | 1331 | `ID`, `PROBA_NUM`, `LAYER_ID`, `POWER_LAYER` |
| `PARAM` | 1316 | `PROBA_NUM`, `PARAMETER_ID`, `VALUE` |

Рабочие связи: `PROBA.ID → GPO.ID` (все 177 уникальных идентификаторов присутствуют в `GPO`)
и `PARAM.PROBA_NUM → PROBA.PROBA_NUM` (1306 из 1331 проб имеют химический анализ).

Слои (`LAYER_ID`), 15 значений: целые `1`…`7` — продуктивные сильвинитовые слои, значения
через дефис `0-1`, `1-2`, `2-3` и далее — междупластья.

Диапазоны величин: `X` 19897–23865, `Y` 8142–13994, `Z` от −449.407 до −380.087,
`POWER_LAYER` 0.02–4.91 м, `VALUE` 0.08–72.69 %. `PARAMETER_ID` всегда равен `1`, что
соответствует KCl.

### Особенности данных, выявленные при анализе дампов

Каждый пункт способен привести к неверному результату без явных признаков ошибки.

1. **Порядок координат в WKT инвертирован относительно `GPO`.** `GEOMETRY.GEOWKT` содержит
   `POINT(Y X)`: например `POINT(13843.5 22472.3)` соответствует записи `GPO` с
   `X = 22472.3` и `Y = 13843.5`. Совпадение подтверждается для 174 из 182 точек. Это
   маркшейдерская система координат, в которой ось X направлена на север — в ТЗ она названа
   вертикальной. Преобразование выполняется единственным выделенным конвертером.

2. **`GEOMETRY.ID` не связан с `GPO.ID`.** Общих значений 22 из 182, и они случайны.
   Заявленная в ТЗ связь по идентификатору в предоставленных данных не работает,
   сопоставление точек выполняется по координатам с допуском.

3. **`GEOMETRY.ID` не уникален** — 5228 строк при 5219 различных значениях. Первичным
   ключом служит `OBJECTGUID`.

4. **Таблица `GEOMETRY` содержит два слоя.** `92E19C56-1E9B-4453-97E9-C881C78CF893` — 182
   объекта типа `POINT`, это и есть пункты опробования. `10780EF5-E5C0-4248-8666-1DCBEFF8071D`
   — 5042 `POLYGON` и 4 `MULTILINESTRING`, графическая подложка.

5. **Десять проб имеют по две записи в `PARAM`** с одинаковым `PARAMETER_ID` и существенно
   расходящимися значениями (проба `235` — 1.25 и 23.54; проба `931` — 43.5 и 17.72).
   Усреднение здесь лишено смысла. Такие пробы исключаются из расчёта, их перечень
   выводится в интерфейсе как предупреждение. Доля — 0.8 % от общего числа.

6. **Одна запись `PARAM` содержит `VALUE = NULL`** (`PROBA_NUM = '1141'`), обрабатывается
   тем же правилом.

7. **Значение `PROBA_NUM = 'р112'` содержит кириллическую букву.** База данных должна быть
   создана в кодировке `AL32UTF8`, дампы читаются как UTF-8.

8. Максимальная длина `GEOWKT` — 2698 символов, в объявленный `VARCHAR2(4000)` укладывается.

## Расчётная часть

Для выбранного набора слоёв в каждом пункте опробования вычисляется:

```
мощность пачки        m = Σ POWER_LAYER
средневзвешенное KCl  C = Σ(POWER_i · KCl_i) / Σ POWER_i
метропроцент          P = m · C
```

Интерполируется `m` для построения изолиний мощностей и `C` для поля распределения целевого
параметра. Метропроцент вычисляется попутно и является основным показателем при подсчёте
запасов.

Пункт исключается из выборки, если в нём отсутствует хотя бы один из выбранных слоёв либо
если какая-либо его проба попала под правило конфликтующих значений. Число фактически
использованных пунктов отображается в интерфейсе постоянно.

Порядок построения:

1. По контуру области строится ограничивающий прямоугольник, по нему — регулярная сетка.
2. Узлы вне контура отбрасываются проверкой принадлежности полигону.
3. В каждом узле вычисляется значение выбранным интерполятором:
   - **IDW** — `z = Σ(z_i / d_i^p) / Σ(1 / d_i^p)`, по умолчанию `p = 2`, с ограничением
     по числу ближайших соседей и радиусу поиска;
   - **Ординарный кригинг** — сферическая или экспоненциальная модель вариограммы,
     параметры nugget, sill и range задаются в интерфейсе.
4. Изолинии извлекаются методом маршевых квадратов на заданных уровнях.
5. Результат выводится в чертёж полилиниями с текстовыми метками.

## Многопоточность

Обращения к `Database` и `Editor` допускаются только из главного потока AutoCAD. Расчёт
выполняется в фоновом потоке, результат передаётся в главный поток через
`SynchronizationContext` и только там записывается в чертёж.

Требуемое ТЗ управление расчётом реализуется штатными средствами: отмена —
`CancellationTokenSource`, пауза с продолжением — `ManualResetEventSlim`, отображение
прогресса — `IProgress<T>`.

## Окружение разработки

Разработка ведётся на Linux, AutoCAD запускается в виртуальной машине с Windows 10 под
KVM. Проекты `Task.Core`, `Task.Data` и тесты собираются и выполняются на хосте, `Task.Plugin`
— в виртуальной машине. Oracle разворачивается в контейнере на хосте и доступен обоим
контурам.

Такое разделение выбрано намеренно: основная сложность задачи сосредоточена в расчётной
части, и она разрабатывается в быстром цикле без запуска AutoCAD.
